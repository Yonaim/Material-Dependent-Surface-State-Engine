# 검증 및 코드 리뷰 절차 (Verification & Review)

> 이 문서는 **무엇을 어떻게 확인할지** 정의한다. 문서 열람·동기화 및 Work Log 의무는 [`Document Workflow`](00_Document-Workflow.md)를 정본으로 따른다.

## 00. 변경 범위 확인

1. 변경하려는 행동과 변경하지 않아야 할 행동을 구분한다.
2. 영향을 받을 호출자, 외부 API, 데이터 형식, 에러 경로, 빌드 구성, 테스트를 확인한다.
3. 관련 [`Requirements`](../../01_Project-Context/02_Requirements.md), [`Constraints`](../../01_Project-Context/03_Constraints.md), [`Contracts`](../../02_Architecture/01_Contracts/00_Contract-Register.md)의 수용 기준을 확인한다.
4. 버그 수정이라면 재현 조건과 기대 결과를 먼저 정의한다. 재현할 수 없다면 불확실성을 명시한다.

## 01. 검증 범위 선택

| 변경 유형 | 우선 검증 | 필요하면 확장 |
|---|---|---|
| 코드 리팩터링 | 기존 동작을 다루는 단위 테스트, 변경 파일 빌드 | 통합 테스트, 성능 회귀 |
| **1단계 섹션 정리** | Region 균형·언어 문법, 선언/멤버 순서/접근 범위 보존, 코드 차이 검토 | 영향이 있으면 빌드·기존 회귀 테스트 |
| **2단계 책임 추출** | 참조 수정, 초기화·종료·리셋·에러 경로·공개 계약 검사, 변경 영역 빌드/테스트 | ABI·레이아웃·직렬화·성능·통합 경로 검증 |
| 신규 기능 | 해당 요구사항의 수용 기준과 새 테스트 | 관련 모듈 통합 테스트 |
| 버그 수정 | 실패 재현 → 수정 후 회귀 테스트 | 인접 경계값과 오류 경로 |
| API/계약 변경 | 공개 인터페이스 소비자 빌드·계약 테스트 | 전체 통합 테스트 및 문서 생성 |
| GLSL / GPU 인터페이스 변경 | 해당 Stage의 셰이더 컴파일·가능하면 SPIR-V 검증, CPU 바인딩·레이아웃·Pipeline 검증 | GPU 실행 결과·경계값·데이터 경쟁·동기화 회귀, 타깃 GPU 검증 |
| 성능 최적화 | 동일 조건에서 정확성·성능 비교 | 장시간·하드웨어별 측정 |
| 빌드·스크립트 변경 | 해당 빌드/스크립트의 구문 검사와 최소 실행 | 다른 플랫폼·환경 |

중첩 Region은 **짝과 포함 관계**, 기본 2단계 규칙, 주석·마커의 들여쓰기 및 접기 지원 여부도 확인한다. 함수 내부에서 중첩했다면 상태 전이·오류 경로·GPU 동기화가 은폐되지 않았는지 검토한다.

- 가능한 한 **작고 빠른 검증부터 시작**하고, 영향 범위에 따라 확대한다.
- 실행할 수 없는 검증은 임의로 대체·성공 처리하지 않는다. 이유와 잔여 위험을 기록한다.
- 실행 명령, 환경, 결과, 실패 원인은 [`Validation and Tests`](../../05_Experiments/01_Validation-and-Tests.md)에 필요한 수준으로 남긴다.

## 02. 변경 결과 리뷰

- [ ] 요구사항·계약을 충족하며 기존 동작을 불필요하게 변경하지 않았는가?
- [ ] 상위 코드의 의도와 제어 흐름이 쉽게 읽히는가?
- [ ] 큰 파일 리팩터링에서 [`1단계 섹션 정리 / 2단계 책임 추출`](../00_Core/03_Section-and-Responsibility-Refactoring.md)을 구별했고, 선언 순서·초기화·ABI 영향을 확인했는가?
- [ ] 공개 API와 데이터 구조 변경에 따른 소비자 영향은 확인했는가?
- [ ] 셰이더 변경이라면 `layout`/Push Constant/Vertex Input과 Host 코드의 대응, Dispatch 경계 및 GPU 동기화를 확인했는가?
- [ ] 에러 경로, 자원 정리, 경계값, 플랫폼별 차이를 확인했는가?
- [ ] 테스트를 실제로 수행했고 통과/실패/미실행을 명확히 구분했는가?
- [ ] 불필요한 디버깅 코드, 로그, 임시 파일, 무관한 변경이 남아 있지 않은가?
- [ ] 코드 주석·Doxygen·영향받은 문서의 동기화 범위를 확인했는가?

### 가독성·공백·Region 리뷰

- [ ] 관련 명령이 같은 그룹에 모여 있고, 다른 단계 사이에 일관된 빈 줄이 있는가?
- [ ] 조건문과 조기 반환이 지나치게 한 줄에 압축되지 않았는가?
- [ ] 의미 있는 큰 작업에만 Region을 쓰고, 단순한 분기마다 만들지는 않았는가?
- [ ] Region의 시작·종료 및 중첩이 균형을 이루는가? 접기 미지원 환경에서도 의미가 보이는가?
- [ ] 줄바꿈·주석 정리 후 원래 표현식·제어 흐름·자료형·GPU 실행 경로가 유지되었는가?

## 03. 작업 종료

- 수행한 검증과 남은 한계를 사용자에게 간단히 보고한다.
- 코드 변경은 [`Work Log`](../../04_Development/01_Work-Log.md)에 한 작업 단위로 기록한다.
- 이 절차는 `git commit`이나 `push` 권한을 부여하지 않는다. 커밋 메시지 작성 규칙은 [`Commit Style`](02_Commit-Style.md)을 참조한다.

## Editor Region 설정 변경 시 확인

- Custom Folding 설정을 변경했다면 GLSL·Shell의 Region 시작/종료 마커가 **LF와 CRLF 파일 모두**에서 인식되는지 확인한다.
- 편집기가 실제로 구간을 접는지 수동 접기와 재열기 후 자동 접기를 구분해 확인한다. 정규식 단위 검사만으로 IDE 기능 검증을 완료했다고 기록하지 않는다.
- 저장소 루트와 하위 볼트의 `.vscode/settings.json`은 자동 병합되지 않으므로 실제 열어 둔 Workspace의 설정 적용 범위를 확인한다.

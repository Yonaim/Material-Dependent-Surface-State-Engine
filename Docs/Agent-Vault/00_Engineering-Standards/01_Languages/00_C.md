# C Engineering Profile

> C는 C++의 부분집합으로 취급하지 않는다. 프로젝트에서 활성화한 C 표준과 컴파일러 확장만 사용하며, [`Code Style`](../00_Core/00_Code-Style.md)의 의도 중심 추상화 원칙을 C 함수·모듈 단위로 적용한다.

## 00. 활성 설정

| 항목 | 프로젝트 값 |
|---|---|
| C 표준 | `{{C_STANDARD}}` (C90 / C99 / C11 / C17 / C23 등) |
| 컴파일러 / 목표 플랫폼 | `{{C_COMPILER}}` / `{{TARGET_PLATFORM}}` |
| 빌드·테스트 명령 | `{{C_BUILD_COMMAND}}` / `{{C_TEST_COMMAND}}` |
| 서식·정적 분석 | `{{C_FORMATTER}}` / `{{C_STATIC_ANALYZER}}` |
| API/심볼 접두어 | `{{C_SYMBOL_PREFIX}}` (없으면 프로젝트 모듈명을 기준으로 지정) |

확정된 표준·플랫폼 제약은 [`Constraints`](../../01_Project-Context/03_Constraints.md)에 기록한다. `malloc`, `strdup`, `getline`, `typeof`, VLA, atomics 등 표준·플랫폼 지원 여부가 다른 기능은 사용 전에 확인한다.

## 01. 상위 프로세스를 먼저 보이는 함수

```c
int app_run(struct app_context *ctx) {
    if (app_validate_config(ctx) != APP_OK)
        return APP_ERROR_CONFIG;

    int status = app_initialize(ctx);
    if (status != APP_OK)
        return status;

    status = app_execute(ctx);
    app_shutdown(ctx);
    return status;
}
```

- 진입 함수는 **무엇을 어떤 순서로 하는지** 보여 주고 복잡한 세부 구현은 하위 함수로 추출한다. 위 예시에서 `app_initialize`는 실패 시 부분 할당 자원을 스스로 정리한다는 계약을 전제한다.
- 의도와 책임이 드러나는 함수명(예: `app_initialize`, `app_execute`)과 명시적인 상태 반환을 사용한다.
- `goto`는 자원 정리·오류 회수처럼 구조가 더 명확해지는 제한적인 경우에 허용한다. 무조건적인 금지·권장을 피한다.
- 재귀·매크로로 제어 흐름을 과도하게 숨기지 않는다.

## 02. 명명 및 모듈 경계

| 대상 | 기본 권고 | 예시 |
|---|---|---|
| 함수 | 모듈 접두어 + `snake_case` | `image_decode_header()` |
| 공개 구조체·typedef | 기존 ABI/라이브러리 관례 우선 | `struct image_decoder` |
| enum | 의미 있는 열거형 이름 | `enum image_status` |
| 상수·매크로 | 충돌 방지용 대문자 접두어 | `IMAGE_MAX_CHANNELS` |
| 내부 심볼 | `static`으로 번역 단위 내부에 제한 | `static int parse_header(...)` |

- C에서 타입마다 Unreal의 `F/T/U/A` 접두어를 자동 적용하지 않는다.
- API 헤더는 명시적인 계약을 제공하고, 구현 디테일은 `.c`에 둔다.
- 외부 공개 함수·타입 접두어는 링커 심볼 충돌과 네임스페이스 부재를 고려해 선정한다.
- 프로젝트에서 이미 확정된 규칙이 있다면 이를 우선한다.

## 03. 메모리·오류·이식성

- 할당/해제의 주체, 소유권 이동, 버퍼 길이, 반환 포인터의 유효 기간을 명확히 한다.
- 길이 검증 전에 버퍼를 인덱싱하지 않는다. 정수 오버플로·부호/크기 변환·널 종료와 경계 조건을 검토한다.
- `errno` 또는 반환 코드 사용 시 실패 경로의 의미가 모호하지 않도록 한다.
- 초기화·정리 실패를 포함해 리소스 누수가 없도록 검증한다.
- 플랫폼 종속 API와 POSIX 전용 API 사용 시 프로젝트 제약을 확인한다.
- 호환되는 컴파일러라면 경고·정적 분석·메모리 검사를 활용하되, **실행하지 않은 검증을 통과로 기록하지 않는다.**

## 04. 주석·Doxygen·문서 동기화

- 일반 주석은 [`Source Comments`](../02_Documentation/01_Source-Comments.md)를 따른다.
- 공개 C API에서 파라미터 길이·소유권·실패 반환값 등 비자명한 호출 계약은 [`Doxygen`](../02_Documentation/00_Doxygen.md)으로 설명할 수 있다. C API의 Doxygen 설명 문장은 한국어를 사용한다.
- 호출 규약·버퍼 계약·반환 코드가 바뀌면 [`Contract Register`](../../02_Architecture/01_Contracts/00_Contract-Register.md)와 관련 테스트 및 Work Log를 동기화한다.

## 05. 파일 내 섹션 구분

- 큰 C 파일에서도 상위 흐름부터 하위 구현 순으로 배치한다.
- 구분이 필요한 경우 [`Local Numbering`](../00_Core/01_Local-Numbering-and-Navigation.md)의 섹션 주석을 사용한다. `#pragma region`은 **비표준 확장**이며 현재 컴파일러와 IDE가 지원할 때만 선택적으로 함께 쓴다.

# 문서 작성 가이드

> **한 줄 요약:** 이 문서는 MDSS Vault 문서를 일관되고 빠르게 읽을 수 있도록 구성하는 기준을 정한다.

이 문서는 MDSS Vault 문서를 일관되고 빠르게 읽을 수 있도록 구성하는 기준을 정한다. 내용의 정확성과 문서별 책임은 [[01_Project-Policy/0000_Documentation|문서 정책]]을 우선한다.

## 문서 최상단 요약

모든 문서는 제목 바로 아래에 핵심 목적이나 결론을 한 문장으로 적는다. 요약은 Markdown 인용문으로 `> **한 줄 요약:** ...` 형식을 사용한다.

## ADR 작성 및 분류

ADR은 `05_ADR` 디렉터리에 평탄하게 둔다. 분류별 하위 디렉터리는 만들지 않고, `Architecture`, `Assets`, `Rendering`, `Simulation` 중 하나를 문서 안에서 지정한다. [[05_ADR/0000-ADR-Index|ADR 0000 색인]]은 이 분류를 기준으로 문서를 모은다.

ADR 상단 메타데이터는 한 줄 요약 뒤에 빈 줄을 두고 다음 불릿 순서로 작성한다. `분류`와 `상태` 불릿은 서로 붙여 쓴다. 관련 문서에는 문서 이름만 적지 말고 Obsidian 링크를 넣는다.

```markdown
> **한 줄 요약:** 결정의 핵심을 한 문장으로 적는다.

- 분류: **Simulation**
- 상태: **Proposed / Accepted / Superseded**
- 날짜: YYYY-MM-DD
- 관련 문서: [[0015-Geometry-Driven-Transport|ADR 0015]], [[04_Architecture/0006_Surface-State-Update|Surface State Update]]
```

날짜를 확인할 수 없는 기존 결정은 추정하지 않고 `미기록`으로 표시한다. 새 ADR은 [[00_Start/Templates/0002_ADR|ADR 템플릿]]을 사용한다.

ADR 색인은 [[05_ADR/0000-ADR-Index|ADR 0000]]에서 분류별로 정리한다. 각 분류에는 `문서 링크`, `안건`, `한 줄 요약` 열을 가진 표를 두고, 제목·요약·분류를 원본 ADR과 일치시킨다. ADR을 추가하거나 이 필드 중 하나를 바꾸면 색인 표도 갱신한다. `05_ADR/README.md`는 색인으로 연결한다.

## 기본 원칙

| 원칙 | 작성 방법 |
|---|---|
| 결론 우선 | 절의 첫 문장에서 결정, 결과 또는 핵심 상태를 먼저 밝힌다. |
| 한 문서 한 책임 | 정책, Architecture, ADR, 구현 계획과 실험 결과를 한 문서에 혼합하지 않는다. |
| 확정도 구분 | 확정 사항, 구현 기본안, 검토 필요 항목을 명시적으로 구분한다. |
| 반복 최소화 | 기준 문서를 링크하고 같은 정의나 수식을 여러 문서에 복제하지 않는다. |
| 검증 가능성 | 구현 또는 실험 문서에는 입력 조건과 기대 결과를 함께 기록한다. |
| 용어 일관성 | [[01_Project-Policy/0001_Glossary\|Glossary]]의 공식 표기와 대소문자를 따른다. |
| 영문 설계 용어 | 문맥상 원래 이름이 더 명확한 기술·설계 용어는 영문으로 유지한다. 세부 기준은 아래 영문 용어 표기를 따른다. |

## 영문 용어 표기

코드 식별자나 설계 개념에 대응하는 이름은 영문 그대로 쓴다. 한국어로 번역하면 원래 개념을 알아보기 어렵거나 코드·관련 문서와 연결하기 어려운 기술 용어도 문맥에 맞게 영문으로 유지한다. 제목, 한 줄 요약, 본문과 표에 같은 기준을 적용한다.

| 문맥 | 사용할 표기 |
|---|---|
| 높이·중력 방향에 의한 Transport 항을 지칭 | `GeometryDrive` |
| 이웃 관계의 전달량 보정 항을 지칭 | `TransferWeight` |
| Virtual Meso Geometry의 높이 성분을 지칭 | Virtual Height. 구현 필드를 직접 지칭할 때는 `MesoVirtualHeight` |

예를 들어 Transport의 역할을 요약할 때는 다음처럼 쓴다.

> Transport에서 `SaturationDrive`, `GeometryDrive`, `TransferWeight`의 역할을 분리한다.

각 용어의 의미와 동작은 자연스러운 한국어로 설명한다. 필요한 경우 첫 등장에 짧은 설명이나 [[01_Project-Policy/0001_Glossary|Glossary]] 링크를 덧붙인다. 일반적인 설명까지 일괄적으로 영문화하지 않는다. 코드 식별자는 backtick으로 표시하고, 공식 용어의 표기와 대소문자는 Glossary 및 실제 코드와 맞춘다.

## 표 사용 기준

여러 항목이 같은 기준으로 반복되거나 서로 비교되는 내용은 표를 우선한다.

| 내용 | 권장 열 구성 | 예시 |
|---|---|---|
| 파라미터 정의 | 이름 / 의미 / 범위 / 기본값 | SRProfile 파라미터 |
| 자료구조 | 필드 / 자료형 / 단위 / 역할 | GPU buffer layout |
| 책임 분리 | 구성요소 / 책임 / 소유 데이터 | Engine module 구분 |
| 선택지 비교 | 대안 / 장점 / 단점 | ADR Alternatives |
| 테스트 계획 | 검증 대상 / 입력·조건 / 기대 결과 / 방식 | Parser validation |
| 일정 | 시점 / 목표 / 산출물 | 주차별 계획 |
| 상태 점검 | 항목 / 상태 / 남은 작업 | Branch 완료 조건 |

표를 작성할 때는 다음을 지킨다.

- 열 제목만 읽어도 비교 기준을 알 수 있게 쓴다.
- 한 행에는 하나의 개념이나 검증 사례만 둔다.
- 수치에는 범위와 단위를 함께 적는다.
- 코드 식별자, 파일 확장자와 값은 backtick으로 표시한다.
- 셀 안에 긴 문단이나 여러 단계의 절차를 넣지 않는다.
- Markdown 표 안의 Obsidian link alias 구분자 `|`는 `\|`로 작성한다.

## 표 대신 다른 형식을 쓰는 경우

| 내용 | 권장 형식 | 이유 |
|---|---|---|
| 처리 순서 | 번호 목록 또는 flowchart | 선후 관계를 명확하게 보여준다. |
| 설계 이유와 맥락 | 짧은 문단 | 인과관계를 자연스럽게 설명할 수 있다. |
| 디렉터리·소유권 계층 | Tree 형태의 code block | 포함 관계를 한눈에 볼 수 있다. |
| 수식 | LaTeX block과 기호 표 | 계산식과 기호 정의를 분리할 수 있다. |
| 실제 API·자료형 | 짧은 code block | 구현 계약을 정확하게 보존한다. |
| 단순 항목 두세 개 | 짧은 bullet list | 표보다 빠르게 읽힌다. |

## 테스트 문서 형식

테스트 문서에는 대상, 입력 조건, 기대 결과와 테스트 방식을 기록한다. 공통 원칙은 [[07_Testing/0000_Testing-Guide|Testing Guide]]에, 구체적인 사례는 주제별 테스트 문서에 둔다. 새 테스트 문서는 [[00_Start/Templates/0005_Test-Plan|Test Plan 템플릿]]을 사용한다.

## 문서 구조

긴 문서는 다음 순서를 기본으로 하되, 문서 책임에 맞지 않는 절은 생략한다.

1. 제목과 상태
2. 목적과 범위
3. 핵심 결정 또는 요약 표
4. 자료구조나 처리 순서
5. 테스트와 완료 조건
6. 미결 사항 또는 제외 범위
7. 관련 문서

## 작성 후 확인

| 확인 항목 | 기준 |
|---|---|
| 경로 | 파일 이동 후 내부 link가 실제 파일을 가리킨다. |
| 중복 | 동일 정의의 기준 문서가 하나다. |
| 표기 | 공식 용어, 확장자와 대소문자가 일치한다. |
| 상태 | 계획과 구현 완료를 구분한다. |
| 표 | 반복 관계는 표로 정리되고 긴 설명은 표 밖에 있다. |
| 코드 | 예시와 현재 자료형·채널 순서가 모순되지 않는다. |

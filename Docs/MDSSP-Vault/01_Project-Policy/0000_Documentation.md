# 문서 정책

> **한 줄 요약:** 현재 시스템의 정본은 적게 유지하고, 같은 내용을 여러 문서에서 반복하지 않는다.

이 볼트의 목적은 **프로젝트를 다시 열었을 때 빠르게 이해하고 바로 개발을 이어갈 수 있게 하는 것**이다. 문서 수 자체를 늘리는 것보다 각 문서의 책임을 분명하게 유지하는 것을 우선한다.

## 볼트 구조

```text
TODO.md                 지금 해야 할 일
Roadmap.md              프로젝트 목표와 큰 마일스톤

01_Project-Policy/      공식 용어와 작성·개발 규칙
02_Research/            외부 연구와 기술 근거
03_Architecture/        현재 시스템이 어떻게 동작하는가
04_Development/         현재 구현·검증·실험에 필요한 문서
05_Decisions/           현재 설계 선택과 근거·대안
06_Assets/              원본 PDF, 이미지와 참고 자료
99_Records/             완료된 계획·개발 이력
```

`Architecture`는 **현재 시스템의 정본**, `Decisions`는 **설계 선택의 근거와 대안**, `Records`는 **완료된 계획·개발 이력**을 담는다. 과거 계획이나 완료된 작업의 상세 순서는 현재 설계 문서와 같은 수준에 두지 않는다.

## 문서별 책임

| 위치 | 무엇을 적는가 | 적지 않는 것 |
|---|---|---|
| `01_Project-Policy` | Glossary, Code/Comment/Commit Style, 문서 규칙 | 기능별 구현 세부사항 |
| `02_Research` | 논문·기술의 원리, 프로젝트 적용 가능성 | 현재 엔진의 정답처럼 단정한 설명 |
| `03_Architecture` | 현재 데이터 구조, 시스템 책임, 알고리즘 계약, 데이터 흐름 | Week/Branch, 완료 대기 상태, 작업 일지 |
| `04_Development/0000_Current-Work` | 아직 Architecture로 확정되지 않은 현재·후속 작업 | 장기 로드맵이나 완료 이력 |
| `04_Development/0001~0005` | 데모, 실험, 검증, 테스트처럼 현재 개발에 직접 필요한 문서 | Architecture의 현재 설계 정의를 반복한 설명 |
| `04_Development/Performance-Results` | 재현 가능한 benchmark 원자료와 자동 생성 summary | 가설·결론을 다시 설명한 문서 |
| `05_Decisions` | 선택한 이유, 대안, 결과 | 현재 시스템 전체 설명 |
| `06_Assets` | 원본 PDF, 이미지와 참고 자료 | 현재 설계의 정본 |
| `99_Records` | 완료된 계획·개발 이력의 요약 | 현재 작업의 정본 |

## 문서 생성 원칙

1. **새 파일을 만들기 전에 기존 문서의 Section으로 넣을 수 있는지 먼저 확인한다.**
2. Week, Branch, 작은 실험 하나마다 문서를 만들지 않는다.
3. 하나의 개념에는 하나의 정본 문서를 둔다.
4. `Architecture`에는 현재 시스템 동작만 적는다. `이번 주`, `구현 대기`, `Branch`, `TODO` 같은 진행 상태는 넣지 않는다.
5. Decision에는 **왜 선택했는가**를 기록하고 Architecture의 현재 설명을 반복하지 않는다.
6. Experiment는 실행 횟수가 아니라 **검증하려는 질문**을 기준으로 묶는다.
7. 같은 개념을 이해하려고 세 개 이상의 문서를 오가야 한다면 문서가 지나치게 분리된 것으로 본다.
8. 임시 메모에 남길 가치가 있는 내용이 생기면 담당 정본으로 옮기고 메모는 정리한다.

## 읽기 쉬운 문서 순서

긴 기술 문서는 가능하면 다음 순서로 작성한다.

1. **이 문서가 설명하는 것** — 한두 문장
2. **직관적인 전체 흐름** — 표 또는 작은 flowchart
3. **핵심 데이터/용어**
4. **실제 처리 순서 또는 수식**
5. **코드와의 대응**
6. **예외·제약**
7. **관련 Decision / Research**

정의를 먼저 길게 나열하기보다, 독자가 먼저 전체 그림을 잡을 수 있게 한다.

## 상태 표기

상태 표기가 필요한 문서에서만 사용한다.

- **현재 설계 기준**: Architecture에서 현재 코드와 설계가 따라야 할 계약.
- **검토 중**: `Current Work`에 남아 있는 아직 선택되지 않은 작업.
- **실험 완료**: Development의 실험/검증 문서에 조건과 결과가 기록된 상태.
- **Accepted / Superseded / Deprecated**: Decision 상태.

설계 문서에 적혀 있다는 사실만으로 구현 완료를 의미하지 않는다. 당장 남은 작업은 [[TODO|TODO]]에서 관리한다.

## 파일명과 번호

- 정식 문서는 디렉터리별 `0000_이름.md` 형식의 네 자리 번호를 사용한다.
- Overview, Guide, Index처럼 폴더의 시작점은 `0000`을 사용한다.
- 번호는 **권장 읽기 순서**를 나타낸다.
- `05_Decisions`의 번호는 기존 Decision ID이므로 유지한다.
- 파일이나 폴더를 옮길 때 내부 링크도 함께 수정한다.

## 템플릿

새 문서가 정말 필요한 경우 `01_Project-Policy/Templates/`의 템플릿을 복사한다.

- `0000_Architecture.md`: 새로운 시스템 정본
- `0001_Implementation.md`: 구현 참고가 독립 문서로 필요할 때
- `0002_Decision.md`: 중요한 기술 선택과 근거
- `0003_Experiment.md`: 하나의 검증 질문에 대한 실험군
- `0004_Bug.md`: 재현 가능한 문제와 수정 기록
- `0005_Test-Plan.md`: 독립적인 회귀 계획이 필요할 때
- `0006_Research-Note.md`: 외부 연구 정리

## 표와 흐름도 사용

여러 항목을 같은 기준으로 비교할 때는 표를 사용한다. 처리 순서는 번호 목록이나 Mermaid flowchart가 더 적합하다. 수식은 LaTeX와 기호 설명을 분리하고, 실제 API·자료형은 짧은 code block으로 적는다.

Flow Map은 별도 문서군으로 늘리지 않고 [[03_Architecture/0010_System-Flows|System Flows]] 한 곳에서 전체 흐름을 연결한다. 데이터 정의나 수식은 각 Architecture 문서를 링크하고 다시 설명하지 않는다.

## PDF와 Markdown

`06_Assets/Documents/`의 PDF는 특정 시점에 검토한 자료와 회의 기록을 보존한다. Markdown은 **현재 설계와 구현 지식**을 갱신하는 정본이다. 둘이 달라지면 오래된 PDF를 현재 정답처럼 수정하기보다 Source Index에서 차이를 표시하고 현재 Markdown을 우선한다.

원본 자료의 역할은 [[06_Assets/Documents/0000_Source-Index|Source Index]]에서 관리한다.

## 작성 후 확인

- 같은 정의가 여러 문서에 반복되지 않는가?
- 제목과 첫 부분만 읽어도 문서 역할을 알 수 있는가?
- 진행 상태가 Architecture에 섞여 있지 않은가?
- 관련 링크가 실제 파일을 가리키는가?
- Glossary의 공식 용어와 코드 식별자가 일치하는가?
- 문서가 없어져도 다른 정본에서 같은 정보를 찾을 수 있는가?
